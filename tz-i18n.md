# Ревью: i18n фронтенда — инвентаризация и план внедрения

> Редакция 3, 2026-10-16 (ред. 2 — привязка к инстансам, §7; ред. 3 —
> строгое ревью плана: тест-инфраструктура §4.5, соглашения §4.4, сборка
> §4.1, приёмка §5.1). Ревью по всему фронту (`frontend/src`, 619 файлов)
> в preparation к внедрению i18n. Инвентаризация выполнена grep-аудитом по
> трём зонам: `views` (101 .vue), `components` (207 .vue), TS-инфраструктура
> (stores / composables / api / utils / platform / pwa / router).
> Все числа — фактические измерения на коммите `1390b7c0` (ветка `dev`).

## 0. Резюме

Фронтенд полностью захардкожен на русском: кириллица в 434 файлах из 619,
≈8 500 строковых литералов (часть — комментарии; реальных пользовательских
строк ≈ 3 000–3 500 значений). i18n-библиотеки нет ни в зависимостях, ни в
коде. При этом проект к i18n **частично подготовлен**:

- **Бэкенд уже хранит язык.** `User.language` — NOT NULL, нормализуется из
  Telegram `language_code` в набор **en / de / es / ru**
  (`backend/app/modules/auth/service.py`, `normalize_language`), правится
  через `PATCH /users/me`, при браузерном входе сохраняется
  `navigator.language` (`stores/auth.ts:209`).
- **`format.ts` locale-aware**: 8 функций имеют параметр `locale = 'ru'` —
  но ни один caller его не передаёт.
- **`utils/plural.ts`** — канонический механизм русских плюралов (3 формы).
- **Секция языка в настройках была и убрана** под i18n:
  `views/user/TimezoneSettingsView.vue` (файл переименован из
  LanguageTimezoneView 2026-09-17, «переключатель вернётся вместе с i18n» —
  дословно в комментарии).
- В `api/errorMessages.ts` зафиксировано решение владельца от 2026-08-16:
  PLAIN RUSSIAN, «full multi-language is its own future task». **Это ревью —
  та самая задача.**

Главный риск не в количестве строк, а в **шести местах, где русский текст
является данными или логикой** (§3.1) — их нельзя перевести механической
заменой строк на ключи.

Целевые локали предлагаем держать в соответствии с бэкендом: **ru (базовая),
en, de, es**.

## 3. Карта рисков: места, где перевод — не замена строки

### 3.1. Русский текст как данные или логика (блокеры механической миграции)

1. **Метод-таксономия — русский текст как формат данных**:
   `methods: string[]` хранится на бэкенде строками `«Направление — Вид»` и
   маркером `«Свой вариант»`; `utils/methodChips.ts` парсит их
   (split по « — », отрезание слова направления, word-stem overlap
   «Круги»/«Женский круг»), `methodTaxonomy.ts` собирает и разбирает.
   Перевод UI не переводит данные — нужен ключевой формат или перевод
   только на границе отображения.
2. **Сравнения с русскими лейблами**: `views/master/MasterPracticesView.vue:273`
   (`rel === 'Сегодня' || rel === 'Завтра'` — лейбл одновременно операнд),
   `views/user/EditProfileView.vue:457` (подтверждение удаления вводом слова
   «УДАЛИТЬ» — на каком языке требовать ввод?).
3. **Regex над русским**: `cleanPracticeTitle` (`\(эфир\)`) +
   дублирующий `.replace` в `UserDashboardView.vue:331`.
4. **Творительный падеж от внешних данных**: `views/user/DetailView.vue:159`
   (`` `${title} с ${name}` `` с fallback «Мастером»),
   `shared/FormShell.vue:87` (`` с {{ practice.master_name ?? 'Мастером' }} ``).
   Для en/de/es конструкция «с X» не переносима — фраза собирается иначе.
5. **Плюрализация**: `plural.ts` — только русская тройка форм; для en/de/es
   нужен `Intl.PluralRules` / встроенные плюралы vue-i18n. Локальные
   дубликаты: `CuratorGroupPageView.vue:439`, `MasterPublicView.vue:410-418`
   (включая капитализированные формы), псевдо-формы «практик(и)» в
   `AdminMasterReviewView.vue:691,695`, вложенные тернарники в
   `PracticeAnalytics.vue:87-95`.
6. **Поиск по русским данным**: `TimezoneCityPicker.vue:96-98` — поиск по
   `city`/`q` (русские имена и латынь); работает на любом языке UI, но
   подписи городов надо брать из серверного каталога (он отдаёт только
   `city_ru/country_ru` — нужен параметр локали на бэке или фронтовой
   переводчик городов).

### 3.2. Прочее

- **Склейка фраз из кусков**: `AdminMasterReviewView.vue:683-699`
  (revokeMessage: 3 литерала + `join(', ')`), `EditProfileView.vue:242-244`
  (METHOD_CHANGE_NOTE из 3 конкатенаций), `adminHelpers.ts formatRelative`.
- **Серверные русские подписи таймзон** (`useTimezoneCatalog` ←
  `city_ru/country_ru`) — фронт не переведёт сам.
- **Контент в БД** (названия практик, направлений, стилей, событий) —
  на русском; это **контентная локализация**, отдельный трек, не UI-i18n.
- **`index.html lang="ru"`** статичен — при смене локали нужно обновлять
  атрибут (и `<title>` остаётся «VELO» — нейтрален).
- **Линт**: `lint-budget.json` — политика нулевой терпимости; стоит добавить
  запрет новой кириллицы вне `locales/` (см. §4.6).

## 4. Рекомендуемая архитектура

### 4.1. Библиотека и структура

- **vue-i18n v10+**, composition API (`useI18n`), `legacy: false`,
  `fallbackLocale: 'ru'`. Единственный зрелый выбор для Vue 3 с плюралами,
  интерполяцией и lazy-загрузкой локалей. Сборка — через
  `@intlify/unplugin-vue-i18n`: сообщения прекомпилируются, и
  рантайм-компилятор не попадает в бандл и PWA-прекеш.
- Локали: **`ru` — в основном бандле** (дефолт, самый полный), `en/de/es` —
  ленивыми чанками через динамический import.
- Файлы сообщений — по доменам, зеркально структуре экранов:
  `locales/ru/{common,auth,user,master,admin,diary,schools,errors}.ts` (или json).
  `errors` — ключи `errors.<backend_code>` (маппинг 1:1 на `ERROR_MESSAGES`),
  сюда же уходят таблицы transcription и store-fallbacks.

### 4.2. Определение и смена языка

1. Источник истины — `authStore.user.language` (сервер уже нормализует).
2. При старте: `i18n.global.locale = user.language ?? 'ru'`;
   для неавторизованных экранов — `'ru'`.
3. Переключатель вернуть в `TimezoneSettingsView` (место подготовлено),
   выбор → `PATCH /users/me { language }` (эндпоинт уже поддерживает) +
   мгновенно в сторе.
4. `document.documentElement.lang` обновлять реактивно.

### 4.3. Форматирование

- `format.ts` и `adminHelpers.ts`: параметр `locale` заменить на чтение
  активной локали (обёртка `getLocale()` из платформенного модуля, чтобы
  utils не зависели от Vue). `ru-RU` в 3 захардкоженных местах views — туда же.
- «Сегодня/Завтра/Вчера» → ключи; **сравнение `rel === 'Сегодня'` в
  MasterPracticesView перевести на код** (`'today' | 'tomorrow'`), лейбл —
  производный.
- Русская таблица сокращений месяцев (`VELO_SHORT_MONTHS`) — оставить
  для `ru`, для остальных локалей — ICU-сокращения.

### 4.4. Соглашения по ключам

- Именование: `домен.экран.элемент` (`bookings.card.statusCompleted`),
  без re-use фраз между контекстами (разные падежи — разные ключи).
- Интерполяция `{name}`, коды ошибок — `errors.<code>`.
- **Плюралы — одним механизмом**: встроенные формы vue-i18n
  (`t('key', n)`, сообщение `год | года | лет`; формы выбирает
  `Intl.PluralRules` — 3 для ru, 2 для en/de/es). `plural.ts` и его
  локальные дубликаты в views удаляются; два сосуществующих механизма —
  гарантированный рассинхрон.
- **Скоуп**: каждый `useI18n()` — только `useScope: 'global'` (дефолт
  создаёт локальный скоуп с пустыми сообщениями — экран молча покажет
  ключи). Фиксируется правилом ревью.
- **Спецсимволы** (`@` — linked, `|` — плюрал, `{}` — интерполяция):
  кодмод обязан их экранировать. На текущем коде проверено — в
  пользовательских строках их нет, но правило остаётся постоянным.
- Типизация: `DefineSchema` на ~3 500 ключей может ощутимо замедлить
  `vue-tsc`. Обязательный минимум — CI-скрипт: сверка «ключ-в-ключ» между
  локалями + проверка, что каждый использованный `t()`-ключ существует.
  Тяжёлая схема типов — опционально.

### 4.5. Тесты

- Тесты **не переписываем массово**: при дефолтной `ru` и сообщениях,
  дословно равных текущим строкам, ассерты продолжают проходить.
- **Инфраструктура тестов** (найдено строгим ревью): 120 тест-файлов
  монтируют компоненты через raw `createApp(...)` и только 5 — через
  `@vue/test-utils`; `test-setup.ts` глобальных плагинов не ставит.
  Фаза 0 обязана дать `installTestI18n(app)` и прогнать кодмод по всем
  120 файлам — иначе первый мигрированный компонент валит свой тест
  (ошибка инъекции `useI18n`).
- Обновляются только: тесты механики локали (новые), тесты мест из §3.1
  (сравнения с лейблами), тесты, фиксирующие строки таблицы ошибок
  (`format.test.ts`, `moodScale.test.ts` и т.п. — если их словари уедут в
  локали).

### 4.6. Защита от регрессии

- ESLint-правило (в связке с lint-budget): запрет кириллических литералов
  в `src/**` вне `locales/` и комментариев — иначе новый русский текст
  будет протекать в каждом PR.
- Правило «никаких сравнений/regex над пользовательскими строками» —
  ревью-чеклист.

## 5. План внедрения

Порядок подобран так, чтобы каждый этап заканчивался зелёным `pnpm verify`
и деплоился независимо (дефолтная локаль `ru` сохраняет тексты дословно).

| Фаза | Содержание | Оценка |
|---|---|---|
| **0. Инфраструктура** | vue-i18n, плагин, `getLocale()`-провайдер, `locales/ru/*` скелет, типизация схемы, обновление `document.lang`, ESLint-правило, тест-хелперы | 1–2 дня |
| **1. Общий слой** | ui-примитивы (7 зашитых мест, включая `VDayPicker`), `router/tabs.ts` (13), таблица ошибок `errorMessages`+`transcription`+28 store-fallbacks+`client.ts` «код», `format.ts`/`adminHelpers`/`periodRange`, `moodScale`, `displayHelpers`, `reflectionVariants`, словари статусов | 3–5 дней |
| **2. Shared-компоненты** | 58 файлов `components/shared` (фильтр-модалки, BookingPopup, Composer, аналитика, шиты) | 4–6 дней |
| **3. Views по ролям** | auth (7) → user (34) → master (33) → admin (23) → shells (3); параллельно рефактор §3.1 (коды вместо сравнений с лейблами, плюралы на Intl) | 10–15 дней |
| **4. Локали en/de/es** | перевод ~3 500 ключей (полный en; de/es), перевод городов/таймзон (нужен параметр локали на `GET /users/timezones` либо фронтовой словарь), manifest description, QA на 4 локалях | 5–8 дней + переводчики |
| **5. Переключатель** | UI в `TimezoneSettingsView` + `PATCH /users/me`, определение при первом входе | 1–2 дня |

Итого механическая часть (0–3, 5): **~3–5 человеко-недель**; переводы —
отдельный поток. Основная неопределённость — §3.1 (таксономия методов и
падежные конструкции): по ним нужны решения владельца до фазы 3.

### 5.1. Пошаговый порядок внедрения

**Инварианты каждого шага** (что делает внедрение постепенным и безопасным):

- ru-каталог дословно равен текущим строкам → ~3 400 тестов проходят без
  массовой переписи; переписываются только тесты механики локали и мест §3.1.
- Каждый шаг — отдельная ветка/PR, заканчивается зелёным `pnpm verify` и
  выкатом на полигон. Пропущенный ключ не ломает экран: `fallbackLocale: ru`
  + `missingWarn` в консоль.
- Механическая замена — кодмодом (скрипт в `frontend/scripts/`), вручную —
  только сложные места из §3 и топ-10 списков аудита.
- Перенос в ключи — **дословно**, без редактуры текстов (иначе всплывёт
  сотня тестовых диффов).
- Прогресс измеряется грепом «кириллические литералы вне `locales/`» по
  директориям; базлайн — числа §2.

**Фаза 0 — фундамент (5 шагов):**
0.1 пакет `vue-i18n` + плагин в `main.ts` (`legacy:false`,
`fallbackLocale` из конфига); 0.2 скелет `locales/ru/` (`common`, `errors`)
+ типизированная схема ключей; 0.3 шов `getLocale()` (без зависимости от

**Фаза 1 — общий слой (3 шага, снизу вверх по зависимостям):**

**Фаза 2 — shared-компоненты (2 шага):**

**Фаза 3 — views (5 батчей; старт — после слияния веток):**
auth (7) → shells (3) → user (34 — допустимо разбить на 2–3 PR) →

рефактор рисков §3.1: сравнения с лейблами → коды (`'today' | 'tomorrow'`),

**Фаза 4 — переводы:** экспорт каталогов скриптом → перевод → заливка:

`manifest` name/description на рантайме не локализуются — это значение

## 6. Открытые вопросы владельцу

1. **Скоуп**: фаза 1 — только UI-хром? Контент (названия практик/направлений/
   методов в БД, строки «Направление — Вид», `languages.ts` «Русский/English»)
   в скооп не входит — подтверждение.
2. **Целевые локали**: en/de/es/ru (набор из `normalize_language`) — финально?
3. **«УДАЛИТЬ»-подтверждение** (`EditProfileView:457`): требовать ввод слова
   на текущей локали или на фиксированной (например, всегда «DELETE»)?
4. **Творительный падеж** («с Иваном»): для не-русских локалей принять

5. **Города/таймзоны**: дождаться серверных `city_en/country_en` или

## 7. Приложение: whitelabel / инстансы (редакция 2, 2026-10-16)

> Скоуп: **только фронт**, бэкенд не меняется. Сверено с архитектурным
> документом «VELO: текущая архитектура и вариант с инстансами школ»
> (16.10.2026): инстанс — та же установка со своим паспортом (домен, бот,
> скин, редакция функций, своя база), скины — значение паспорта по
> контракту «пакет, проверяемый по схеме», функции — целыми редакциями.
> Вывод: план §4–5 совместим с этой архитектурой без переделки; четыре
> дополнения к фазе 0 ниже.

### 7.1. Как план ложится на архитектуру инстансов

| Механизм архитектуры | Что это даёт i18n-плану |
|---|---|
| **Паспорт инстанса** (домены, роль, ключи — значения конфигурации) | Источник локал-конфига: набор локалей, локаль по умолчанию, имя бренда. Едут в сборку фронта как `VITE_*` при выкате — каждый инстанс собирает фронт сам, отдельной сборочной механики не нужно (пункт §7.2.2 прежней редакции закрыт) |
| **Скин, слой 1** (токены и ассеты на постоянной раскладке) | Забирает визуальный бренд целиком: переопределение набора `--velo-*` из `styles/variables.css`, логотип, иконки `public/icons/*`, `theme-color`, `manifest.ts`. Бренд-имя в строках — интерполяция `{brand}` со значением из паспорта (~8 мест, §7.2 п.3) |
| **Редакции функций** («школа», «школа с платежами», «полная»; экраны выключенного модуля выключены) | Структура каталогов §4.1 — не «по экранам», а **по модулям** (namespace = модуль бэка): чанки локалей ленивые, инстанс без модуля их чанк не грузит. Роут-гейт по эндпоинту «что включено» — фронт-работа вне i18n, но раскладка каталогов под неё закладывается сейчас |
| **PRIDEM / primer.yaml** | Уровень деплоя, фронт-план не затрагивает |
| **Сервер никогда не уникален; скин — данные, не сборка** | Переопределения сообщений (терминология школы) — тоже данные: опциональное значение паспорта в формате базовых каталогов, проверяется той же схемой; применяются `mergeLocaleMessage` на старте. В контракт скина их не включать — скин визуален по определению документа |
