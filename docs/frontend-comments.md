# Стандарт комментариев фронтенда VELO

Обязателен для всего кода в `frontend/**` (`.ts`, `.vue`, `.mjs`, конфиги, тесты).
Проверяется гейтом `frontend/scripts/no-cyrillic.mjs` (см. §7) — зелёный `pnpm lint`
означает соответствие инвариантам §1 и §7.

Основа: классическая практика «why, not what» + TSDoc-совместимый JSDoc
([tsdoc.org](https://tsdoc.org)) + правила читаемости для ИИ-агентов (агенты —
постоянные читатели этого кода: ищут grep'ом, читают файлы чанками, верят
тексту комментариев слепо).

---

## 1. Язык: английский, ноль кириллицы

- Проза комментариев — только английский (технический, без идиом, сарказма,
  эмодзи и ASCII-арта). Кириллица в комментариях запрещена полностью.
- Ссылка на UI-копирайт — **ключом каталога**, не цитатой:

  ```ts
  // Плохо:  // the user sees «Вас пригласили в школу» BEFORE any booking
  // Хорошо: // the user sees the invite copy (i18n:schools.transfer.invite) BEFORE any booking
  ```

  Формат маркера: `i18n:<dotted.key>`. Гейт проверяет, что ключ разрешается
  в `src/locales/ru/` (резолвер `key-audit.mjs`); опечатанный или выдуманный
  ключ = ошибка линта.
- Динамические ключи: цитируем выражение из кода (оно ASCII), маркер не нужен:
  `` // resolves via `t(\`report.reasons.${code}\`)` ``
- Строки, которых в каталоге нет (инстанс-данные skin/PWA, сборные строки):
  английское описание. Если без дословного литерала непонятно — оставить
  `// TODO(i18n-ref): <почему>`: это очередь на ручной разбор, не решение.
- Примеры кода в JSDoc — ASCII-плейсхолдеры; реальный копирайт только через
  `i18n:<key>` в соседнем комментарии.

## 2. Два вида комментариев

### 2.1 Doc-комментарии `/** ... */` — JSDoc (TSDoc-совместимый)

Охват: все экспорты (composables, stores, api, utils, platform) + неочевидные
внутренние функции. Правила:

- **Первая строка — самодостаточное резюме** одним предложением. Это то, что
  агент видит в grep-выводе и outline; детали — в `@remarks`.
- **Самодостаточность**: у читателя нет IDE-hover; никаких «as above»,
  «см. выше» — комментарий читается изолированно от любого места.
- Теги (единственный разрешённый набор): `@remarks`, `@param`, `@returns`,
  `@defaultValue`, `@throws`, `@deprecated`, `@example`, `{@link ...}`,
  `@internal`.
- Аннотации типов запрещены: `@param {string} x` → `@param x - ...`. Типы
  выводит TS, генератору доков они не нужны.
- `@param` / `@returns` — только когда семантика неочевидна из имени и типа.
  **Никогда не пересказывать имя** (`@param name - The name.` — шум).
- `@deprecated` — всегда с заменой: `@deprecated Use loadSchools() instead; removed in FE-200`.
- Кросс-ссылки — тегами: `{@link useCursorPagination}`, `@see tz-i18n §4.6`,
  `@see FE-123`. Агент может грепнуть связанный символ и пойти по графу.
- Ссылки на tz-доки, тикеты (`FE-123`/`BE-123`), пути и имена символов —
  сохранять дословно, это grep-якоря.

### 2.2 Строки `//` — не входят в генерацию доков

- Объясняют **«почему», а не «что»**: намерение, инварианты, допущения,
  edge cases, бизнес-правила. Что делает код — видно из кода и имён.
- Размещаются рядом с кодом, который ограничивают.
- **Шум не переводят, а удаляют**: комментарий, пересказывающий код, не имеет
  ценности ни для человека, ни для агента. Протухший комментарий хуже
  отсутствующего — агент верит ему слепо; при переводе сомнительный
  комментарий удаляем, а не сохраняем в англ. виде «на всякий случай».

## 3. Грамматика и стиль

- Полные предложения: заглавная буква, точка в конце (для многострочных);
  императив для директив: `Return null when the school was deleted.`.
- Без сокращений в прозе — агенты грепают полные слова (`organization`, не
  `org`). Канонические идентификаторы — исключение: `FE-123`, `tz-i18n`,
  `:schoolId`.
- Английский US.

## 4. Терминология и глоссарий

Словарь кода, без транслитерации. Синоним-якорь указываем в комментарии,
если читатель может искать под другим словом.

| RU-понятие | Термин в коде | Примечание |
|---|---|---|
| школа | `school` | legacy-код/тесты могут содержать `group` — переименование FE-127; в новых комментариях только `school`, у stragglers допустимо «legacy: group» |
| мастер (исполнитель) | `master` | |
| куратор школы | `curator` | |
| практика | `practice` | |
| запись на практику | `booking` | |
| заметка дневника | `diary entry` | kinds: check-in / feedback / note |
| каталог строк | `catalog` | `src/locales/<locale>/<domain>.json` |
| скин / вайтлейбл | `skin`, `whitelabel` | инстанс-данные через passport, не хардкод |

## 5. Тесты

- Комментарии в тестах — по этому же стандарту (английский).
- Пинящий русский копирайт **текст строк** не трогаем: тесты намеренно
  утверждают отрендеренный текст из ru-каталога (tz-i18n §4.5).

## 6. Режимы действия стандарта

- **Перевод существующего кода**: консервативно — перевод + нормализация в
  теги только когда семантика уже есть в тексте («возвращает null, если…» →
  `@returns Null when…`). Новые `@example` не выдумываем.
- **Новый код**: полный стандарт; `@example` с input→output — для нетривиальных
  юнитов (пример избавляет читателя-агента от чтения имплементации).

## 7. Инструментальный контроль

- `no-cyrillic.mjs`: (а) строки и шаблоны без кириллицы вне `locales/`
  (tz-i18n §4.6); (б) комментарии без кириллицы во всех сканируемых файлах,
  включая тесты; (в) каждый `i18n:<key>` в комментарии разрешается в
  ru-каталоге.
- `key-audit.mjs` (tz-i18n §4.4) — существующий аудит ключей.
- Опционально в будущем (отдельные тикеты, не сейчас): `eslint-plugin-tsdoc`
  как синтаксический линт doc-комментариев; `typedoc` + `pnpm docs` для
  генерации доков из §2.1.
