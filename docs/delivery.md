## PR и коммиты

- Фронт доезжает PR'ом в `deploy-machine`, слияние — кнопкой «Create a merge commit» (не squash). Бэк пока пушит в ветку напрямую — защиты ветки нет до ruleset из FE-222.
- В каждом коммите после пустой строки — трейлер `Task: <код задачи>` (например `Task: FE-189`), одним блоком с `Co-Authored-By`. Это практика проекта.
- Ветки после мержа не удаляются: PR ставятся друг на друга стопками.
- Перед мержем — `gh pr update-branch <номер>`, чтобы база вливалась в ветку и CI перегонял её ещё раз (практика оркестратора, не защита репозитория).

## CI на deploy-machine

Полные правила — в шапках самих workflow; здесь карта.

- **«CI»** (`.github/workflows/ci.yml`) — гейт поставки; состав джобов и правила — в шапке файла. Матрица сборки (`matrix — gate`) собирает ядро без пакета, два синтетических пакета и два настоящих (`velo-brand`, `goodo-brand`): PR, после которого пакет бренда не собирается или теряет токены и ассеты, красный. Неочевидное: docs-only PR зелёный за секунды (`scope`), coverage-рейтчет — `frontend/coverage-budget.json`, бюджет бандла — `docs/agents/bundle.md`, smoke образа проверяет `/config.json` и закрытые `/health`, `/ready` (404), sweep блокирующий (FE-222). Обязательный статус — `CI — gate`.
- **«Bundle budget»** (`bundle-budget.yml`) — метки бюджета: поднятый бюджет — `bundle-growth`, поднятый потолок — `bundle-ceiling`. Обязательный статус ruleset (FE-222).
- **«Review risk»** (`review-risk.yml`) — уровень ревью R1/R2/R3 (FE-279, `docs/review-risk.md`): считает минимум по диффу правилами из базовой ветки, краснеет, если строка `**Ревью:**` в PR ниже минимума, и ставит метку `review:R*` (её ставит CI, не человек). Перезапускается на push, правку описания и смену меток. В ruleset не входит; красная проверка останавливает мерж-гейт оркестратора.
- **«Backend tests»** (`backend-tests.yml`) — сьюта бэка на живых Postgres, Redis и RustFS (BE-197). Временный: удаляется, когда velo-test сам гоняет тесты перед каждой миграцией.
- **«Primer check»** (`primer-check.yml`) — `pridem check`: репо глазами машины (`primer.yaml`, `primer.lock`, compose стеков). Идёт на каждый PR, без paths-фильтра.
- **«e2e sweep»** (`e2e-stack.yml`) — ночной обход в 02:30 UTC на ветке по умолчанию, Chromium + WebKit; руками — «Run workflow». Инструкция — `docs/agents/e2e.md`.
- **«Visual»** (`visual.yml`) — пиксельная сверка base vs head на каждом из двух скинов (`velo-brand`, `goodo-brand` по `.github/brand-skins.json`, по job на скин). Строгая: любое расхождение вида на gold или goodo — красный CI; задуманное изменение автор подтверждает меткой `visual-change` (ставит человек, не агент). Обязательный статус — `visual — verdict` (запускается всегда, одно имя); job `visual — base vs head (<скин>)` обязательным не делают.
- **«Commit msg»** (`commit-msg.yml`) — тема каждого коммита PR в формате `KEY-N: …` или `… (owner ГГГГ-ММ-ДД)` (`scripts/check-commit-msg.sh`). Идёт на каждый PR, без paths-фильтра; PR ботов и PR ствол → ствол пропускает. Обязательный статус `commit subjects` (FE-222).
- **«Codec vector»** (`codec-vector.yml`) — сверка двух таблиц кодека (бэк и фронт), по paths-фильтру.
- **«token-sync»** (`token-sync.yml`) — спит с 2026-11-09 (решение владельца): истина токенов — код, Figma — зеркало.

## Фронт под машиной Праймера

Контракт рантайма — [`tz-whitelabel.md`](../tz-whitelabel.md) и `primer.yaml`; здесь — карта поставки.

- Образ фронта собирает машина при установке из репозитория (`frontend/Dockerfile`). Значения инстанса приходят при старте контейнера в `/config.json`: адрес API и бота, языки, опции (шесть флагов `OPTION_*`, `telegram` обязателен — `primer.yaml: options`).
- Типы API генерирует и машина: секция `types` в `primer.yaml`, на роли test она коммитит их ключом `velo-types`. Пока в CI жив drift-check, изменение API приносит перегенерированный `frontend/src/api/generated.ts` в той же поставке.
- Редакция одна — `ai` (`editions.json`): что видно на экране, решают флаги опций, а не редакции.
- Пакеты инстанса — слоты `primer.yaml: packages`: скин (контракт `>=2,<3`, необязательный: без пакета в паспорте — нейтральное ядро, FE-230; золотой VELO — пакет `velo-brand`) и texts (`apply: runtime`, `/srv/texts`, `/texts/ui/`). Пакет texts может нести `comms/**`, но машина его пока не монтирует (`primer.yaml`).
- Место скина в сборке — `frontend/public/skin` от корня репозитория (контекст сборки фронта). Пакет из приватного репозитория машина читает своим ключом развёртывания (deploy key только на чтение, DM-127): публичность репозитория пакета ей не нужна.

### Проверка пакета скина до выката

Так же, как машина при `apply: build`: пакет целиком в место сборки, затем сборка образа фронта. Команды — из корня репозитория; `<пакет>` — **абсолютный** путь к каталогу пакета на нужном теге (у `goodo-brand` — его `skin/`): `apply-skin.mjs` ищет его от текущего каталога, а первая команда — `cd frontend`.

```sh
cd frontend
node scripts/apply-skin.mjs <пакет>          # = pnpm skin: копия целиком + validate-skin
PRIMER_EDITION=ai pnpm build                 # validate-skin --build первым шагом
grep -o '"name":"[^"]*"' dist/manifest.webmanifest   # имя бренда, не VELO
cd ..
docker build -f frontend/Dockerfile --target runtime --build-arg PRIMER_EDITION=ai \
  --build-arg PRIMER_RELEASE=skin-check --build-arg PRIMER_COMMIT=$(git rev-parse HEAD) -t velo-frontend:skin-check .
docker run --rm -d --name skin-check --add-host app:127.0.0.1 -p 18080:3000 \
  -e API_BASE_URL= -e TELEGRAM_BOT_URL=https://t.me/example_bot -e LANGUAGES=en,ru,uk -e DEFAULT_LANGUAGE=en \
  -e OPTION_PAYMENTS=true -e OPTION_SCHOOLS=true -e OPTION_MCP=true -e OPTION_ZOOM=true -e OPTION_TELEGRAM=true -e OPTION_LLM=true \
  velo-frontend:skin-check
curl -s localhost:18080/manifest.webmanifest       # name, theme_color пакета
docker rm -f skin-check
node frontend/scripts/apply-skin.mjs --remove      # назад к нейтральному ядру
```

`--add-host app:127.0.0.1` нужен только для проверки: nginx фронта при старте ищет upstream `app`. Пакет в `frontend/public/skin` игнорируется git (`frontend/.gitignore`).

## Скины: gold и goodo

Скина два, gold и goodo, каждый в своём репозитории; какие они, что скин может и чего нет — `tz-whitelabel.md` §3.5 (единственное место). Ядро без пакета нейтральное по цветам, шрифту, ассетам и имени: вместо имени бренда — слово `App` в `<title>`, манифесте и строках (FE-231). Адрес поддержки — только `supportEmail` бренд-записи (контракт `2.2`, FE-251); у ядра и у пакета без поля строки с адресом нет.

### Новое поле бренд-записи: порядок выката

Поле бренд-записи (или новый файл пакета, как набор иконок настроения `assets/mood/` в `2.3`, FE-273) появляется с новым минором контракта скина (`2.1` — `contrastExceptions`, `2.2` — `supportEmail`, `2.3` — иконки настроения, `2.4` — токены веса `velo.fw.*`). Читатель младшего минора отвергает незнакомое поле и незнакомый файл, поэтому порядок такой:

1. Мерж velo с новым минором. Закрепления в `.github/brand-skins.json` остаются на старых тегах: в них поля нет, и CI зелёный.
2. Мерж PR бренда, который поднимает `contract` и вписывает поле. Тег ставит владелец.
3. PR velo поднимает закрепление бренда до нового тега: матрица и «Visual» проверяют пакет с полем.
4. Паспорта инстансов переводят на новый тег. Пакет с новым полем на стенде со старым velo не соберётся, поэтому паспорт идёт после выката velo.

Бренд без поля ничего не делает: пакет младшего минора читается как прежде.

Токен реестра, который пакет задаёт сам (`velo.fw.medium` и `velo.fw.bold`, `2.4`, FE-278), идёт по тому же порядку: `validate-skin` требует контракт `2.4`, а velo без токена отвергает его как неизвестный. Пока закрепление на старом теге, значения токенов — значения ядра, вид не меняется. Подъём закрепления на тег с тремя начертаниями шрифта поднимает и precache золотой сборки (все начертания пакета входят в него): метка `bundle-growth` у человека, `skinned` в `frontend/bundle-budget.json` — в том же PR.

### Закрепление в CI

Версии скинов (тег и коммит каждого) закреплены в `.github/brand-skins.json`, версий здесь нет. `.github/scripts/fetch-brand-skins.mjs` клонирует пакеты на раннер и проверяет, что тег указывает на закреплённый коммит. Новый тег бренда принимается PR'ом, который меняет закрепление:

- матрица (`matrix — <скин>/ai`) сверяет сборку: бренд, токены, ассеты, шрифт, число чанков;
- «Visual» собирает base с закреплением из base-версии `brand-skins.json`, head — со своим, поэтому отчёт показывает, что новый пакет меняет на 19 ключевых экранах (`frontend/e2e/visual/screens.ts`). Подъём тега меняет вид, поэтому такой PR несёт метку `visual-change` (её ставит человек, сверив отчёт); без неё Visual красный.

Репозитории брендов сейчас публичные: CI читает их анонимно. Станут приватными — нужен ключ на чтение в секрете `BRAND_REPO_TOKEN` (fine-grained token на оба репозитория); выпускает и подключает его владелец. Скрипт передаёт ключ заголовком через окружение git, в `.git/config` и в текст ошибок он не попадает. Без секрета приватный репозиторий валит ячейки матрицы и ячейки `e2e-a11y` (axe на обоих скинах) на шаге загрузки с подсказкой про `BRAND_REPO_TOKEN`; `ci.yml` передаёт секрет в `e2e-a11y` явно. PR из форков секреты не получают: на них матрица и «Visual» с приватными брендами красные.

### Скины: проверка вида

Экран, вид которого зависит от скина, смотри на обоих. В PR строка «Проверено на скинах» (`.github/pull_request_template.md`): `gold` / `goodo` / `не влияет`.

- **Сборка и «Visual» локально.** Пакет — абсолютный путь к `skin/` нужного тега. Из `frontend/`: `node scripts/apply-skin.mjs <пакет>`, `pnpm build`, затем `sh e2e/visual/run.sh <dist-базы> dist` (`docs/agents/e2e.md`); `node scripts/apply-skin.mjs --remove` убирает пакет. Дев-сервер (`vite`) раскладывает токены, но не логотипы, фон и онбординг: вид скина проверяй сборкой.
- **Стенды владельца** (`~/work/velo-dev`, вне репозитория): `velo-dev` — золотой VELO за туннелем `dev.velo-test.xyz`; `goodo-dev` — локальный стенд Goodo (`goodo-dev-up.sh`, `goodo-dev-status.sh`, `goodo-dev-down.sh`). `velo-dev-skin.sh goodo|velo` переключает, на какой из двух ведёт кнопка меню дев-бота.
- **Веб-консоль `/admin`** (до FE-272 — `/console`, старые адреса ведут туда же). Смотри в окне браузера 1440, 1280 и 768 (меню на 768 свёрнуто в полосу иконок); телефонное окно показывает заглушку. Вид обоих скинов держат Visual (14 экранов консоли в окне 1280×800), axe и детектор вёрстки `sweep-console` (`docs/agents/e2e.md`). Меню собирается по опциям инстанса: без `payments` нет «Финансов», плитки выручки и колонки «К выводу», без `schools` — «Школ и компаний», без `zoom` — вкладки Zoom у практики. На цвета и тени консоли влияют только токены скина; текст прямо на фоне страницы (хлебные крошки, подписи групп меню) берёт `--velo-text-on-bg-muted`: у goodo фон — градиент, и серый `--velo-text-muted` на нём ниже 4,5:1.
- **Что смотреть:** контраст текста на карточках и на фоне, шрифт (длинные строки и кириллица), логотип (у goodo логотип свой, у gold — мандала и словесный знак), фон, иконки. Золотой вид — ожидаемый по макету; вид goodo — по `goodo-brand`.
